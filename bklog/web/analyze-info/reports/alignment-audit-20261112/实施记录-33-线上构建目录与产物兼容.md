# 线上构建目录与产物兼容

## 源链路及问题

原 `bklog/Makefile build-web` 执行 `cd web && npm install --legacy-peer-deps && npm run build`。根 build 已转调 V3，但安装仍作用于 web 根目录的旧依赖树；V3 又默认输出到自身包内 dist，导致 Make 成功不代表后端能找到新首页。

V2 的 `packages/web-v2/webpack.config.js` 将产物写到 `bklog/static/dist`。后端 `config/default.py` 的模板目录、MAKO_TEMPLATE_DIR 和 VUE_INDEX 仍从该目录读取 index.html；home_application 和 log_adapter 的首页渲染继续依赖此约定。

V2 的 LogWebpackPlugin 还负责插入服务端环境变量模板、将首页资源改为 `${BK_STATIC_URL}/...` 及生成 asset-manifest.js。BK_STATIC_URL 由后端上下文提供为 STATIC_URL + dist，可能包含应用子路径或 CDN。V3 原构建缺少这层模板契约，且生产初始化不会像开发模式一样请求环境接口，所以不能只移动文件夹解决上线问题。

## 实现

- Makefile 改调 `web/scripts/build-web.mjs`，只在 V3 包内使用 frozen-lockfile 安装和构建。无全局 pnpm 的 npm 构建宿主可用 npx 启动包中声明的固定 pnpm 版本；不回退到根目录或 V2 安装。
- 安装显式包含构建所需 devDependencies，避免宿主设置 NODE_ENV=production 后省略 Vite；构建子进程固定 production，避免误用开发代理配置。Make 目标声明为 PHONY。
- V3 主应用默认 outDir 改为 `bklog/static/dist`，与 V2 相同。后端模板、服务器静态目录及现有发布路径不变。显式 Vite outDir 仍可用于仓库外隔离验证。
- 新增 `production-paths.mjs` 作为默认输出目录的唯一配置；封版静态交付检查同步使用该目录。
- `runtime-environment.html` 保留 V2 的完整服务端变量协议，包括原始 JSON/布尔值和 RUM 配置占位符；只保留模板表达式，不保存真实值。测试逐字比较 V2 模板，防止漏字段或类型变化。
- `production-delivery.mjs` 为主应用生产 HTML 注入模板和服务端标题，转换模块脚本、CSS 和 favicon 资源前缀；在 Vite 最终解析 HTML 资源占位符后再次检查，避免 favicon 留在相对页面路径。JS/CSS 内部资源使用 Vite 相对资产解析；不把服务端模板表达式写入 JS chunk。
- 补齐与 V2 相同命名/前缀协议的 asset-manifest.js。主应用包含封版 legacy-v1 产物，未修改其压缩资源。
- 生产构建不读取本地 .env.local、V2 local.settings 或 Cookie；开发代理行为保留。增加 BK_STATIC_URL 的 Window 类型声明。
- 封版资源解析优先使用后端 BK_STATIC_URL，避免把应用页面根路径误认为静态资源根路径；开发环境继续使用 Vite base。

## 产物中发现并修复的问题

原检索 Worker 的诊断 URL 使用普通 new URL 指向源码，Vite 把该 TS 当作静态文件输出，虽然实际 Worker 构造走的是编译路径。检索和聚类 URL 获取器改用 `?worker&url` 的编译资产地址，保留原 Worker 构造、消息、错误返回和生命周期。

新增 `verify-production-build.mjs`：检查模板、首页引用、文件存在性/路径边界、CSS 资源、manifest、原始 TS/JSX、Source Map 和本地配置文件。原始 TS 不再进入主应用产物。

## 实际验证

- 使用真实 `CI=true make -C bklog build-web` 完成依赖安装、Vite 构建和两个交付检查。验证环境为 Node 24.21.0、pnpm 10.32.1。安装读取已提交锁文件，没有修改依赖版本或锁文件。
- 补充实际 `CI=true NODE_ENV=production make -C bklog build-web` 验证，完整成功；npm-only 合成宿主也验证了固定版本引导、两个命令的工作目录及构建子进程的 production 环境。
- 最终默认产物在 `bklog/static/dist`：641 个文件；首页三项资源引用（JS、CSS、favicon）均带服务端静态前缀。没有原始 TypeScript、JSX、Source Map 或本地配置文件。
- 实际 Mako 引擎用从零构造的合成上下文渲染产物，根路径、应用子路径及 CDN 前缀三组通过，50 个模板变量全部可解析；没有保存真实环境渲染结果。
- 产物中未发现本地 Cookie 完整值；完整扫描与构建输出只在仓库外。
- 封版静态交付 215 个文件校验通过；runtimeAccepted 仍为 false，不宣称封版 V1 完整运行验收通过。
- APM/Trace 各 8 个必要导出、52 个文件及当前源码摘要校验通过；相较旧产物去掉了多余原始 Worker 源文件。库构建不注入主应用 HTML 模板、不写主应用目录。既有 package:apm/package:trace 仍负责交付到 web/monitor-apm-retrieve 和 web/monitor-trace-retrieve，隔离构建目录不当作发布目录。
- 定向测试 9/9 通过，覆盖 V2 模板协议、路径、缺失资源、私有文件/源码拒绝、npm-only 宿主命令隔离、封版字体及部署路径。
- 全量测试 471 项中 465 通过，原有六项失败不变；严格类型仍为 1562 条已有诊断，无新增模式。AI Native 索引和差异检查通过。

## 本地复验及回滚

从仓库根目录运行 `make -C bklog build-web`；直接在 web 执行 npm run build 也使用同一 V3 默认输出和产物检查。不要同时运行 V2/V3 主应用构建，两者按兼容约定写同一个目录。

本次开始前的本地 V2 生成产物已移到仓库外临时归档，路径为 `/private/tmp/bklog-production-v2-dist-before-20261116`。这里只是本地回滚备份，不替代线上发布平台的版本回滚，也没有上传构建产物。

本次未修改 V2 源码、未启动或发布线上服务、未提交或推送。服务端真实部署仍需在授权测试环境验证登录、接口、CDN CORS 和嵌入宿主，不把模板/静态校验等同于完整业务发布验收。
