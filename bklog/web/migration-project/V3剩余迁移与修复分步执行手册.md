## 2 固定约束

1. 不简化、删减或自行补充业务逻辑。原操作、状态、权限、校验、异常、取消、重试、存储和外部协议均须有迁移去向。
2. 先分析 V2 组件、依赖和调用，再写 Vue3；浏览器用于确认行为和 UI，不以截图代替源码分析。
3. 业务直接使用 TDesign 的原生属性、事件、插槽和类型。把旧 API 换名转接、全局别名或透传壳不能算完成。
4. 可以保留有明确业务职责的组合组件和 Hooks，例如字段配置、结构化错误展示、未保存确认；其接口应清晰表达业务，不继续伪装成整套旧组件库。
5. 检索时间选择继续使用官方 Vue3 `@blueking/date-picker`，不重新实现时间组件。其他旧 `bk-date-picker` 调用逐项判断，不能全部误认成这一豁免。
6. 第三方包内部依赖的 `bkui-vue` 等原名，只能由明确的第三方兼容边界接住；V3 业务源码不能借此继续导入旧控件。不能直接改 node_modules 或压缩产物作为交付。
7. 后端 API、DTO 业务语义、空间头、认证、权限、路由参数和嵌入协议保持不变。无法从源码确定的行为先记为待核实，不猜测。
8. 保留当前所有未提交修改；不得 reset/clean、覆盖用户修改、自动合并另一迁移分支。新模型先核对差异再动文件。
9. 不靠 any、ts-ignore、关闭 strict、缩小 include/exclude、空类型声明或组件占位壳让检查变绿。
10. 不复制整套 V2 class。样式针对 TDesign 实际 DOM 和本项目主题做还原；保留业务自定义类，避免前缀替换误伤。
11. 未验证的写入流程不得标通过；禁止修改或删除已有业务资源。测试新增资源必须有唯一名称和清理记录。
12. 不自动发布、推送、升级包版本或切换线上流量；构建、隔离产物和部署验证与真实发布分开。

## 5 每一小批固定执行流程

1. 领取 R 编号和具体小模块，先读上批交接和当前 git diff，确认基线与允许修改文件。
2. 从 `source-map.json` 找到 V2 路径，核实 V2 实际入口、父组件、store、services、指令、样式、条件分支和测试。
3. 写行为契约：输入值/空值、props、事件顺序与载荷、插槽、实例方法、状态转换、校验、权限、异步、取消、清理、持久化和 URL。
4. 在 V2 跑最小可复现场景，保存足够对照证据。无法运行的分支不靠猜测填实现，先做源码契约和可重复测试，运行验收保持待验证。
5. 核实本地锁定 TDesign 版本的类型和实现；官方 MCP 文档作辅助。确定旧 API 到原生 API 的逐项映射。
6. 先做 1～3 个文件的完整试点。通过后按同契约扩展，通常每批 5～15 个业务文件；有特殊行为就拆批，不把整个 233 处输入当一次简单替换。
7. 先跑关联逻辑/组件测试和必要类型检查，再跑共享回归；保留真实请求、权限和错误反馈。测试操作真实函数和事件结果，不只断言标签名。
8. 在 16176 及模块实际管理入口对照浏览器；修差异后保存稳定截图。离线 fixture 不能替代真实业务验收。
9. 刷新调用台账和 AI 索引；更新任务记录、差异和失败记忆。共享组件修改要回归之前已验收模块。
10. 交接时分别写“源码转换、业务验证、视觉验证”的结论。连续两轮失败先停止批量扩展，复盘根因，不叠加更多兼容层。

### 5.1 必备行为契约内容

每个迁移单元至少记录：V2 来源路径与符号、V3 文件与符号、旧输入和输出、新控件协议、保留的业务函数、场景与失败分支、测试定位、截图、当前结论。

## 6 验证命令和正确解释

除注明外，以下命令从 `packages/web-v3` 执行，日志目录需由本批先建立。

```sh
pnpm --ignore-workspace ai:context --module=retrieval --limit=30
pnpm --ignore-workspace ai:impact src/features/retrieval/workspace/search-result/index.tsx --limit=30
node tools/business-control-audit.mjs
node tools/check-source-layout.mjs
node tools/check-source-syntax.mjs
pnpm --ignore-workspace typecheck
pnpm --ignore-workspace test
pnpm --ignore-workspace ai:index
pnpm --ignore-workspace ai:check
pnpm --ignore-workspace build
pnpm --ignore-workspace build:apm
pnpm --ignore-workspace build:trace
pnpm --ignore-workspace verify:v1
pnpm --ignore-workspace acceptance:business
```

`ai:impact` 先按工具实际支持的路径格式核实输出，不以返回空列表证明无影响。`ai:context` 的模块名按当前工具/索引核实，不能凭目录名臆造。

执行 `node tools/business-control-audit.mjs --write` 会更新 `ai-native/business-controls.json`，默认命令只检查。余额未归零时默认检查失败是正确结果。`--write` 的成功退出码只表示盘点完成。

`check:source` 与严格 typecheck 当前允许作为已知失败基线记录，不能因此跳过。阶段规则是“不新增诊断且逐步减少”，最终要求两者都通过。`typecheck:regression` 是历史基线辅助比较，不能替代 `typecheck`，也不能用旧归档基线冲淡当前新增问题。

每条命令单独记录原始退出码。已知失败可以记录后继续排查，但不能用 `|| true`、管道最后一项的退出码或仅匹配日志中的 PASS 将失败改成通过。

类型比较必须按“文件、错误码、完整消息、出现次数”做多重集合差分，忽略纯行号变化；总数降低也可能同时新增严重错误。最终退出码仍须为 0。

构建通过只证明产物可生成。`build` 中 V1 的 STATIC_DELIVERY_VERIFIED 不代表运行通过；`verify` 当前也不能替代旧调用清零、严格类型和全业务验收。

源码和构建输入固定后再依次构建主应用、APM、Trace。期间修改 `src`、配置、锁文件或构建工具时，作废受影响构建并重跑。两份 Monitor 产物应具有相同 sourceDigest/buildConfigDigest。不要为了留下新的 PASS 反复运行已通过且未受影响的检查。

依赖已就绪也不要求一次完成一个大 R 任务。对子任务建议命名 `R08-01`、`R08-02`，标出模块和剩余节点；下一次仍调用 R08，直到所有节点通过后再关闭任务。

以下情况先停止扩大修改范围，继续不受影响的分析/测试，并记录阻塞：

- 不知道 V2 实际功能或分支，只能凭截图猜。
- 登录/测试资源不足，无法验证真实写入或宿主集成。
- 新增类型错误、关键业务回归、共享样式影响已验收页面。
- 同一问题两轮修复失败，尚未确认根因。
- 源码或构建配置变动，旧验证摘要已失效。
- 存在未提交工作冲突，无法确定哪部分属于当前任务。

业务样本参数不是可用存储、主机和仓库资源清单；用户允许新建测试资源也不允许编辑/删除已有数据。遇到环境缺项写具体缺什么，不降低验收标准。
