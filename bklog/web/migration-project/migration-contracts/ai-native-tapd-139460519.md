# Vue2 → Vue3 + 新组件库 + AI Native：可直接交给 AI Agent 执行的实施计划

背景：
当前运行版本（Vue2）bklog/web/src

目标V3版本：bklog/web/packages/web-v3
目标版本组件库：[https://tdesign.tencent.com/vue-next/getting-started](https://tdesign.tencent.com/vue-next/getting-started)

新版分支命名：feat/ai-migration-engine

## 一、实施目标与总体策略

最终目标

将 Vue2 项目迁移到 Vue3，并替换基础组件库，同时建立可复用的 AI Native 开发与验证机制。

第一优先级：业务保真

旧版已有的业务行为、数据流、组件事件、校验、权限、异常处理不得因迁移而无故丢失。

第二优先级：UI 保真

以旧版真实运行效果为基准，逐步恢复基础组件、业务组件和页面的视觉效果，而不是让 AI 自行设计新 UI。

第三优先级：可持续 AI 化

把迁移知识、组件契约、执行流程和质量门禁沉淀为工程资产，供后续开发、重构和模型切换复用。

### 实施约束

1. 以旧版源码、真实运行行为和测试结果为事实依据，不以现有不完整的 Vue3 实现作为唯一依据。
2. 不一次性重写整个项目，按依赖关系和业务模块分批迁移。
3. 先恢复业务行为，再完成组件库适配和视觉精修；对有依赖关系的任务可以并行准备，但不能跳过验收。
4. 不允许 Agent 自行删除无法理解的逻辑，也不允许通过降低测试标准来宣布完成。
5. 每个阶段必须有明确的产物、执行命令、验收结果和下一阶段准入条件。

## 二、把整个工程拆成 8 个可执行阶段

下面的计划可以直接转换成 Agent 的任务队列。

### P0

工程初始化与基线冻结

建立迁移工作区、分支策略、运行环境和质量门禁基础。

阶段产物：可重复运行的旧版基线与工程配置

### P1

旧项目自动化分析

扫描路由、组件、状态、事件、API、样式和依赖关系。

阶段产物：源码分析报告与迁移风险清单

### P2

业务行为与 UI 基线建立

采集关键交互、组件状态、页面截图及验收场景。

阶段产物：业务行为矩阵、截图基线、测试清单

### P3

迁移引擎与组件适配层

建立组件契约、Vue3 迁移规则、新组件库 Adapter。

阶段产物：可复用的迁移规范和适配组件

### P4

典型业务模块试点迁移

完整执行迁移、E2E、视觉回归和差异修复闭环。

阶段产物：一个通过门禁的端到端迁移模块

### P5

按依赖顺序批量迁移

基于试点模板，逐模块迁移并独立验收。

阶段产物：全量迁移任务及模块验收记录

### P6

全量回归与上线准备

执行功能、视觉、兼容性、构建与发布验证。

阶段产物：完整回归报告与上线检查表

### P7

AI Native 能力固化

将规则、Skills、上下文管理、失败记忆和影响分析固化。

阶段产物：可重复运行的 AI 工程工作流

推荐执行顺序：P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7。

其中 P3 的基础设施可以与 P1、P2 的部分工作并行准备，但 P4 必须建立在真实基线和基本迁移契约之上。P5 只有在 P4 验收通过后才能正式启动。

AI Native 的设计从第一天就要考虑，但不应该以先开发一套庞大的 Agent 平台为前提。先把迁移闭环做实，再把有效的能力抽象为通用工具。

## 三、先建立统一的工程工作区

建议不要一开始就把所有迁移逻辑写成一段超长的 Agent Prompt。应当把执行计划、项目事实、迁移契约和验证结果分开管理。

### 3.2 工程初始化要求

P0 阶段让 Agent 先检查并确认：

* 旧版 Vue2 项目路径与当前 Vue3 项目路径。
* 两个项目使用的包管理器、Node 版本、构建工具和启动命令。
* 旧版与新版的路由、状态管理、组件库和 UI 样式体系。
* 当前测试框架、可用测试环境、认证方式与 API 依赖。
* Git 分支、工作区状态、未提交代码和现有迁移成果。

`migration.config.json` 可以采用如下结构作为起点：

```
{
  "sourceProject": "../legacy-vue2",
  "targetProject": "../target-vue3",
  "componentLibrary": {
    "source": "AUTO_DETECT",
    "target": "TO_BE_CONFIRMED"
  },
  "migration": {
    "strategy": "incremental",
    "preserveBusinessBehavior": true,
    "requireVisualVerification": true,
    "requireRegressionTests": true
  },
  "qualityGates": {
    "buildMustPass": true,
    "criticalFlowsMustPass": true,
    "unresolvedDifferencesMustBeReported": true
  }
}
```

这是配置模板。Agent 必须先确认真实目录、依赖和目标组件库，再填写具体值，不得将示例路径直接当作项目事实。

## 四、每个阶段的具体执行任务

### P0：工程初始化与基线冻结

准入阶段

任务清单：

* 检查旧版、新版代码仓库及 Git 工作区。
* 确认旧版可启动、可登录、可访问关键业务页面。
* 记录 Node、包管理器、构建工具、测试工具和启动命令。
* 记录 Vue2、新版 Vue3 与两代组件库的准确版本。
* 冻结旧版基线，保留原始代码、配置和样式。
* 创建迁移分支，确保不覆盖用户现有修改。
* 确认旧版与新版的测试数据和运行环境。
* 生成 `01-baseline-and-environment.md`。

通过标准： 旧版运行方式已确认，目标仓库状态已记录，关键页面能够访问，迁移范围明确。无法运行的部分必须形成阻塞清单，不得假装基线已经完成。

### P1：旧项目自动化分析

事实提取

按以下顺序实施：

1. 扫描项目文件、路由和页面入口。
2. 使用 AST 和模板解析提取组件注册、组件引用、Props、事件、指令和插槽。
3. 分析 Mixins、Watchers、生命周期、状态管理、事件总线和 `$refs` 调用。
4. 提取 API 调用、数据模型、表单校验、权限控制与异步逻辑。
5. 提取全局样式、局部样式覆盖、主题变量、深度选择器和组件库专属 CSS。
6. 构建页面—组件—状态—API—样式依赖关系。
7. 结合 AI 进行语义分析，补充业务说明、迁移风险和待确认事项。

每一条分析结果必须记录来源文件及代码位置；AI 推断的内容要与静态扫描的确定性事实分开标记。

必须交付：

* 页面与路由清单。
* 组件全量清单及引用关系。
* 高风险 Vue2 特性清单。
* 业务数据流和事件关系图。
* 样式与组件库耦合清单。
* 迁移风险报告。
* 未能静态识别、需要运行时确认的行为列表。

通过标准： 所有路由入口均已纳入清单，关键组件引用关系可追踪，所有已识别的高风险特性都有处置策略。

注意：静态分析只能说明源码中能被识别的内容，并不能证明运行时行为完整。动态组件、反射调用和后端业务规则等必须单独核验。

### P2：业务行为与 UI 基线建立

这是解决你当前功能丢失和 UI 还原度低的核心阶段。

具体任务：

1. 根据页面清单确定高、中、低风险页面。
2. 为关键页面编写业务操作场景。
3. 在旧版环境执行这些操作，记录真实输入、输出和状态变化。
4. 通过 Playwright 或现有自动化工具采集旧版截图。
5. 对复杂组件采集不同状态的截图。
6. 将截图、交互场景、测试数据与对应源码建立关联。
7. 为尚未确认的行为创建待确认项，不允许 Agent 自行补全。

建议每个关键场景都采用统一格式：

```
scenario_id: SEARCH-001
page: "<真实页面标识>"
priority: critical

preconditions:
  - "<前置状态>"

actions:
  - "<用户操作>"

expected:
  ui_state: "<预期 UI 状态>"
  business_result: "<预期业务结果>"
  emitted_events: []
  api_effects: []
  error_behavior: "<异常处理预期>"

verification:
  e2e: required
  visual: required
  contract: optional
```

这里的字段需要依据项目实际情况填写。不能把 `api_effects` 为空理解成没有 API 调用，也不能因为某个场景暂时没有测试脚本，就将其视为非关键功能。

通过标准： 所有关键业务路径都有明确的预期结果，核心页面具有可重复的截图基线，复杂组件的主要交互状态已有记录。

### P3：迁移引擎与组件适配层

此阶段先开发最小可用能力，不要一开始就追求全自动迁移平台。

任务拆分：

| 任务 ID | 实施内容 | 验收结果 |
| --- | --- | --- |
| P3-01 | 建立 Vue2 → Vue3 兼容规则集 | 已知破坏性变更均有检测或处置规则 |
| P3-02 | 建立业务组件契约格式 | 输入、输出、状态和不变量可机器读取 |
| P3-03 | 建立基础组件适配层 | Button、Input、Select 等 API 有统一映射 |
| P3-04 | 建立样式令牌体系 | 全局设计变量和关键控件样式可统一管理 |
| P3-05 | 建立契约测试模板 | 组件输入输出和状态转换可自动验证 |
| P3-06 | 建立视觉差异工具 | 能够采集、对比、保存差异报告 |
| P3-07 | 建立任务与产物追踪 | 每次变更可关联需求、契约、测试和结果 |

每个任务都要先检查仓库中是否已有可复用实现，禁止为满足计划而重复造轮子。

通过标准： 基础设施可以在一个真实业务组件上运行，而不是只有接口定义、空目录或演示代码。

### P4：典型业务模块试点迁移

核心验证阶段

这一阶段决定整个方案是否值得批量推广。

选择一个包含以下至少几种复杂行为的业务模块：

* 表单与多字段联动；
* 查询、筛选、分页或表格操作；
* 自定义业务组件；
* 弹层、插槽或跨组件事件；
* 异步请求、权限或异常恢复。

不要选择只有静态文本、按钮和简单布局的页面作为唯一试点。

#### 具体执行流程

1. 读取该模块的旧版源码、行为矩阵、组件契约与截图基线。
2. 识别 Vue2 兼容问题和组件库差异，生成迁移实施计划。
3. 迁移依赖的基础组件与业务组件，优先保持对外业务契约稳定。
4. 迁移页面状态、事件链、请求逻辑、权限和异常处理。
5. 执行构建、静态检查、组件契约测试和单元测试。
6. 运行 E2E 测试，逐条核对旧版行为预期。
7. 运行视觉回归，对比默认态、交互态、异常态和弹层。
8. 修复差异，重新执行受影响的测试，生成完整验收报告。

试点的完成条件不是“页面能运行”，而是：

* 关键业务路径全部通过；
* 已识别的原有业务行为均有明确去向；
* 未实现的功能与尚未解决的差异全部显式登记；
* 关键 UI 差异经过修复和复核；
* 构建、测试和截图结果均可复现。

如果试点失败，必须先分析失败根因并修正迁移规则、适配层或测试方法，不能直接把同一套不成熟流程推广到所有页面。

### P5：按依赖顺序批量迁移

试点通过后才进入批量迁移。

建议按下面的顺序安排任务：

批次 A：基础设施与通用组件

基础组件、公共指令、通用 Hooks、状态管理适配、全局样式。

批次 B：复用型业务组件

搜索栏、表单封装、可编辑表格、权限操作、通用弹层等。

批次 C：业务页面与流程

按组件依赖和业务流程分组，先迁移依赖清晰、风险可控的模块。

批次 D：高风险、强耦合模块

复杂编辑器、递归组件、跨模块状态、拖拽交互及特殊渲染逻辑。

每个批次都使用相同的任务模板：

1. 确认变更范围和依赖。
2. 读取对应契约和旧版证据。
3. 生成迁移差异清单。
4. 实施迁移。
5. 执行针对性测试。
6. 执行受影响模块的回归测试。
7. 生成差异与验收报告。
8. 验收通过后再进入下一批次。

如果团队有多个 Agent，可以并行处理依赖已明确且互不冲突的任务。例如，业务行为分析和截图采集可以并行；多个 Agent 也可以分别迁移不同的独立组件。

但是，共享基础组件、全局样式、路由配置和状态管理等高冲突文件应设置单一负责人。不能让多个 Agent 同时修改同一份工作区代码而不进行隔离。

### P6：全量回归与上线准备

必须覆盖：

* 全量路由和页面访问；
* 核心业务流程；
* 权限和角色差异；
* 表单校验、异常提示和请求失败恢复；
* 浏览器控制台错误与未处理 Promise 异常；
* 关键页面视觉对比；
* 生产构建、资源路径、路由刷新和部署配置；
* 旧版与新版的业务结果差异。

如果需要对照旧版与新版的业务结果，尽量使用相同测试数据和等价的操作步骤。不要因为两套环境的数据状态不同，就直接将结果差异判定为迁移缺陷或忽略差异。

最终交付：

* 全量页面迁移清单；
* 关键业务场景回归报告；
* 视觉差异汇总；
* 未解决问题与风险清单；
* 生产构建与部署验证结果；
* 发布及回滚方案。

### P7：AI Native 能力固化

这一阶段的重点不是再写一套只针对本次迁移的 Prompt，而是把已经验证有效的执行机制沉淀成工具。

建议优先实现：

1. 迁移规则库：按 Vue3 兼容、组件库适配、业务保真、视觉还原分类。
2. 按需加载 Skills：仅在相关任务中加载组件迁移、UI 回归或复杂交互分析规则。
3. 变更影响分析：根据组件依赖图找到受影响页面和测试。
4. 上下文压缩：向执行 Agent 提供当前任务相关源码、契约、依赖和失败记录，而不是整个仓库。
5. 失败记忆：保存已确认的缺陷原因、修复方式、适用范围和回归测试。
6. 自动质量门禁：统一构建、契约、E2E 和视觉验证的结果格式。
7. 模型无关的执行接口：Agent 可以切换 Codex、Cursor、Claude 或其他模型，但必须遵守相同的任务协议和验收标准。

这里可以复用你已有的本地 Coding Robot 思路：让路由器判断任务类型与复杂度，再调用分析、实现或验证 Agent；模型可以替换，但迁移契约与质量门禁不能因模型不同而改变。

## 五、为 AI Agent 定义统一的任务协议

这是实际执行时最关键的部分。无论你后续使用哪种 Agent，都不应该只给它一句“把这个页面迁移成 Vue3”。

每个任务必须包含输入、范围、约束、产物、验证和停止条件。

建议所有任务都采用以下结构：

```
task:
  id: "P4-MODULE-001"
  phase: "P4"
  type: "migration"
  title: "迁移指定业务模块"

inputs:
  source_files: []
  target_files: []
  contracts: []
  baseline_screenshots: []
  related_tests: []

scope:
  allowed_changes: []
  forbidden_changes:
    - "删除未确认的业务行为"
    - "修改未纳入任务范围的模块"
    - "降低或删除既有质量门禁"

requirements:
  preserve_business_behavior: true
  preserve_component_contracts: true
  require_visual_verification: true
  require_regression_tests: true

outputs:
  - "变更文件清单"
  - "业务行为差异报告"
  - "组件契约差异报告"
  - "测试结果"
  - "视觉差异报告"
  - "剩余风险清单"

completion:
  build_passed: true
  critical_tests_passed: true
  unresolved_differences_reported: true
```

以上是任务协议模板，具体路径、测试列表和约束应由 Planner 根据项目实际情况生成。

### 任务执行状态

建议统一定义以下状态：

`PENDING → ANALYZING → PLANNED → IMPLEMENTING → VERIFYING → ACCEPTED`

同时允许进入：

* `BLOCKED`：缺少必要信息、环境或依赖；
* `FAILED`：实施或验证失败；
* `NEEDS_REVIEW`：存在业务歧义或需要人工决策。

Agent 不得因为代码已修改就把状态改成 `ACCEPTED`。只有验证程序和验收规则满足要求，才能接受任务。

### 失败后的处理规则

| 失败类型 | Agent 应当执行的操作 |
| --- | --- |
| 编译失败 | 读取真实报错，定位变更范围内的兼容问题 |
| 业务测试失败 | 对照旧版行为契约检查状态、事件与数据流 |
| 视觉差异过大 | 分类差异，检查设计令牌、组件默认样式和 DOM 结构 |
| 缺少旧版证据 | 暂停相关修改，补充源码分析或运行时观测 |
| 环境或认证失败 | 登记阻塞原因，不得将测试标记为通过 |
| 多次修复仍失败 | 输出最小复现、尝试记录和待决策事项，避免无限循环 |

建议设置可配置的重试上限，例如同一缺陷连续两次修复仍失败，就先重新分析根因，再决定是否继续，而不是让 Agent 不断追加补丁。

## 六、可直接复制到 Codex / Cursor / Claude Code 的主执行指令

下面这份指令用于启动整个工程。它的职责是建立计划和执行基础，不是让 Agent 立即开始全量迁移。

# Vue2 → Vue3 + 新组件库 + AI Native 迁移工程总控指令

## 一、角色与目标

你是本项目的迁移工程负责人，负责将现有 Vue2 项目升级到 Vue3，并将旧基础组件库替换为指定的新组件库，同时建立可持续的 AI Native Web 工程规范。

本任务不是简单的代码转换，而是以旧系统为事实依据的行为保真迁移。

最高优先级：

1. 保留已有业务行为、数据流和组件交互。
2. 恢复并验证原有 UI 视觉效果。
3. 保证迁移后的代码可维护、可测试。
4. 将有效的分析、迁移、验证流程沉淀为可复用的工程能力。

## 二、执行原则

1. 先分析，后规划，再实施，最后验证。
2. 未完成旧版基线和迁移范围分析前，禁止全量重写。
3. 不得擅自删除、简化或替换无法理解的业务逻辑。
4. 不得仅凭组件名称相似，就认为新旧组件行为相同。
5. 业务行为、UI 视觉、构建与运行质量必须分别验证。
6. 所有分析结论尽可能关联源文件、代码位置、运行证据或测试结果。
7. 区分静态分析确定的事实、AI 推断、待确认事项和已经验证的结论。
8. 不得通过删除测试、缩小测试范围、屏蔽错误或降低验收标准来获得通过结果。
9. 每个任务限定变更范围，禁止无关重构。
10. 用户已有的未提交修改必须受到保护。

## 三、阶段执行顺序

严格按照以下顺序推进：

P0：工程初始化与旧版基线冻结。
P1：旧项目静态分析和依赖关系提取。
P2：业务行为矩阵、组件清单与 UI 基线建立。
P3：迁移契约、Vue3 兼容规则、组件适配层和验证工具建设。
P4：选择一个真实复杂业务模块进行完整试点。
P5：按照依赖关系分批迁移其余模块。
P6：全量业务、视觉、构建和部署回归。
P7：固化 Skills、上下文管理、失败记忆和质量门禁。

任何阶段未达到验收条件，不得默认进入下一阶段。

## 四、当前启动任务

现在只执行 P0，并为 P1 建立准备条件。

### P0-01：检查仓库

识别并记录：

* Vue2 源项目路径；
* Vue3 目标项目路径；
* Git 分支及未提交修改；
* Node 版本、包管理器、构建工具；
* Vue、路由、状态管理、组件库和测试工具版本；
* 现有启动、构建和测试命令。

不得猜测项目路径或覆盖现有文件。

### P0-02：验证运行环境

在不破坏现有环境的前提下，检查旧版能否启动、能否访问关键页面，以及新版当前能够运行到什么程度。

对于需要登录、后端服务或特定数据的页面，记录所需条件和当前阻塞。

### P0-03：确定迁移范围

区分：

* 必须迁移的业务功能；
* 必须保留的自定义组件；
* 计划替换的基础组件库；
* 已有 Vue3 实现中可以保留的成果；
* 已知缺失或行为不一致的功能。

不得将尚未核验的现有 Vue3 实现认定为正确基线。

### P0-04：生成交付物

创建或更新：

* migration-plan/00-scope-and-goals.md
* migration-plan/01-baseline-and-environment.md
* migration-plan/07-risk-register.md

记录实际发现、证据、未知事项和后续任务。

如果仓库尚无合适目录，可以创建迁移工作区，但不要为了匹配模板重构业务代码。

## 五、P0 验收标准

只有在以下条件满足后，才能将 P0 标记为 ACCEPTED：

1. 旧版和新版仓库位置已经确认。
2. Git 工作区状态和用户现有修改已经记录。
3. 主要依赖版本和可用执行命令已经核实。
4. 旧版运行状态及运行阻塞已经如实记录。
5. 迁移范围、目标组件库和关键未知项已明确。
6. 所需报告已生成并能够被其他 Agent 读取。

无法满足的条件必须标记为 BLOCKED，并说明原因，不得伪造结果。

## 六、阶段完成后的输出格式

每次任务完成后，输出：

1. 任务 ID 与状态；
2. 实际完成的工作；
3. 变更文件列表；
4. 执行的命令与真实结果；
5. 业务行为及视觉方面的发现；
6. 未解决问题与风险；
7. 验收条件逐项结果；
8. 下一阶段的建议任务。

不要在 P0 完成前直接迁移整个项目。先交付真实的工程基线、差异和风险报告，再根据这些事实规划 P1。

使用方法： 把上面的指令交给 Agent 后，让它先完成 P0。等 Agent 输出实际仓库情况后，再生成基于真实目录、依赖版本和组件库的 P1 任务，不要预先假定项目使用某种组件库或构建工具。

## 七、如何把主指令转化为可持续运行的 Agent 任务队列

我建议你最终让本地 Coding Robot 或其他 Agent 按下面的方式运行：

Planner：生成任务

读取当前阶段、迁移报告和未解决问题，生成有限范围、具有明确验收标准的任务。

Executor：执行任务

读取任务契约和相关上下文，修改指定范围内的代码，记录变更与不确定事项。

Verifier：验证结果

执行对应的构建、单测、契约测试、E2E 和视觉回归，输出机器可读取的结果。

Reconciler：处理差异

区分代码缺陷、业务歧义、环境问题和基线问题；必要时回退到分析或计划阶段。

Artifact Store：沉淀成果

保存契约、测试报告、截图、失败原因和已验证的规则，供下一任务按需检索。

这个设计不要求一开始就实现五个独立 Agent。初期可以由同一个 Coding Agent 依次承担这些职责，只要每个阶段的输入、输出和验收边界独立。等工作流稳定后，再拆分成多 Agent 调度。

## 九、你现在应该如何启动
