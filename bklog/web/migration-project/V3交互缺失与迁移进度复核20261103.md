# V3 交互缺失与迁移进度复核

> 本文记录修复前复核状态；随后完成的管理布局与集群基础交互修复见《V3管理布局与集群交互修复20261103.md》。官方时间面板随后修复，见《V3官方时间组件弹层修复20261103.md》；其余问题仍按本复核追踪。

日期：2026-11-03。范围：当前工作区源码、R00～R03 任务记录、16176 检索及同业务 ES 集群管理的 V2/V3 只读对照。本轮分析没有修改业务代码，没有提交表单或操作已有业务资源。下文 src/、tests/ 和构建配置路径均相对 packages/web-v3。

## 结论

**当前 V3 不能按“全业务已迁移、只剩样式优化”的版本验收。当前状态是 Vue3 兼容运行、部分原生组件完成、核心业务控件协议仍未迁移完。**

本轮实际复现了时间选择无法展开可操作面板、集群新建无法打开表单、管理页面被压进左侧窄栏。源码中同时存在表格列空壳、Form/Drawer/Select 旧属性直接传给 TDesign 的情况。这些问题会让入口看起来还在，但点击后没有相应界面，或后续状态/校验/事件不工作。

检索初始化、结果与趋势加载仍能运行，不能据此推导时间选择、详情、菜单、管理表单等完整交互已通过。也没有证据证明最近的 Loading 改造“删除了所有事件”：管理宿主和时间面板缺陷在此前 R01/R02 记录中已存在，后续局部 Loading 工作尚未修复这些阻碍。

## 2 本轮实际复现的交互问题

### F01 管理内容被当成菜单内容渲染

优先级：P0。证据：本轮浏览器复现及源码确认。

同样的业务参数下，V2 集群管理使用左侧导航加完整主内容区；V3 的标题、新建按钮、搜索和空态被挤在左侧约一个菜单宽度内，右侧大片区域没有业务内容。

源码依据：

- `src/features/management/manage/index.vue:33` 仍使用旧 Navigation 布局，`#menu` 和默认插槽承担导航与主内容两个职责。
- 该文件 `:76` 的 navigation-content 包含最终 router-view。
- `src/platform/compat/tdesign/magic-controls.ts:310` 将 bkNavigation 直接接成 TDesign Menu，而没有保留布局容器的职责。
- `legacyControl` 在 `:109` 只代理注册，没有转换布局协议。

根因：Navigation 与 Menu 的职责不同。TDesign Menu 不能直接承载原 Navigation 的布局协议。这个问题影响管理页宽度、控件可见范围、弹层触发区域和后续交互，不是增加 top/width 覆盖就能完整解决。

修复方向：按 V2 布局关系使用明确的布局容器和原生菜单，让 router-view 位于主内容区；保留权限、导航状态、分组、外链和折叠逻辑。作为 R16 的独立宿主修复子批次优先处理。

### F02 新建集群按钮不能打开表单

优先级：P0。证据：本轮同入口点击对照及源码确认。

- V2：点击“新建”，出现基础信息、集群名称、英文名称、地址、端口、协议、用户名/密码、连通性测试、提交和取消。
- V3：点击“新建”，没有出现上述表单，页面仍是左侧窄栏。
- 本轮没有填写连接信息，没有点击连通性测试或提交。

源码依据：

- `src/features/clusters/current/cluster-manage/es-slider.tsx:1553` 附近继续传 `before-close`、`is-show`、`quick-close`、`transfer`、`onAnimation-end`、`onShown`。
- `src/platform/compat/tdesign/magic-controls.ts:330` 只是将 bkSideslider 接到 Drawer。
- 当前原生 Drawer 使用 visible/onClose 等协议，没有自动认识上述旧属性和事件。

根因：按钮入口和业务状态函数保留，不等于原生抽屉的可见状态、内容插槽、初始化与关闭链路已经连接。

修复方向：R11 先做一个完整原生 Drawer 业务试点，显式连接 visible、内容/页脚、打开初始化、关闭来源和未保存拦截；随后验证校验与提交。不能只让抽屉外框出现就标完成。

### F03 检索时间选择没有可操作面板

优先级：P0。证据：本轮复现现象；底层定位来自已有 R02 证据。

在 16176 点击“近 15 分钟”：V2 出现常用时间、日期选择、相对范围、确定和时区设置；V3 本轮点击后没有出现这些可操作内容。检索结果仍能加载，说明页面能查询并不代表时间交互有效。

R02 已有记录进一步指出：官方 Vue3 DatePicker 的懒渲染面板在兼容运行时中被 tippy 转移后脱离文档；其调用侧 modelValue/format/timezone 未发现错误。此前局部原生运行时岛实验又因依赖图跨运行时生命周期问题回退。该底层 DOM 过程本轮没有重新跟踪，不冒充新的根因验证。

修复方向：保留官方 `@blueking/date-picker`，针对完整 SDK 和其 TDesign 适配依赖图处理运行时/面板所有权。先用最小复现证明预设、绝对范围、时区、清空及关闭都可操作，再回接主应用。不要重写时间组件、修改压缩包或再次只隔离一半依赖。

## 3 源码确认的其他高风险缺口

以下是当前代码中可以确认的协议缺口，不等同于本轮已经执行所有写入场景。

### F04 表格列和设置仍有空壳

`magic-controls.ts:338` 将旧表格直接接到 Table；`:339`、`:340` 的 TableColumn 和 TableSettingContent 仍是 passthrough，最终只输出一个 div。

管理集群表格 `index.tsx:665` 附近仍使用旧分页事件，`:672` 开始以旧子列声明 prop/label/renderHeader/单元格插槽。原生 TDesign 需要明确的 columns/cell/title、rowKey 和分页/筛选事件映射。

本轮 V2/V3 的 ES 集群数据都为空，不能据此说丢失了已有集群数据；但 V2 能呈现完整专用表头和页面结构，V3 没有相同呈现。其他数据链路列表的零高度行问题有此前 R03 证据，本轮未逐页重测。

影响：列内容、操作按钮、列设置、排序、筛选、选中、展开等会被成片遗漏。修复应为 R13/R14 的完整列表闭环，不能继续复用透传列壳。

### F05 表单属性和校验返回值尚未适配

`es-slider.tsx:1063` 仍传 model，字段仍用 property；当前 TDesign Form 使用 data，FormItem 使用 name。`magic-controls.ts:303`、`:304` 没有做相应转换。

`es-slider.tsx:373` 直接 await validate 后继续构造请求。原生 Form 的 validate 可 resolve 为 boolean 或错误对象；仅 await 而不判断结果，不能继续沿用旧库“失败必然进入 catch”的假设。

影响：绑定/校验可能失效，甚至在校验失败时仍进入后续动作。本轮未提交该表单，属于源码确认风险，需通过 R10 的真实校验与请求断言验证。

### F06 Select 的值和选项语义仍不完整

`magic-controls.ts:314`、`:329` 将旧 Option/Select 直接接到原生组件，业务中仍可见旧 id/name、popover 扩展属性和旧事件。当前 TDesign Option 主要使用 value/label。

影响：选项可能显示却无法正确选中、状态回填丢失、下拉扩展区域失效。需要逐场景验证，不可统一将所有值转为字符串。本轮没有操作所有选择器，保持待验证。

### F07 仍依赖兼容运行时

实际 4175 构建链从 `vite.config.ts` 进入 `vite.application.config.mjs`；后者在 `:94` 使用模板 MODE 2，在 `:147` 将 vue 指向 compat 运行时。`native-sdk-vue.ts` 也导出 @vue/compat，并为指定 SDK 设置局部 MODE 3。

这是一条 Vue3 兼容迁移链，不是纯原生 Vue3 完成状态。复杂组件、SDK DOM 转移、slot/model/event 的组合行为仍需专门验证。不能直接把全局 MODE 改为 3 或同时加载两份运行时，来掩盖尚未升级的 Class/SDK 依赖。

## 4 为什么测试和构建通过仍会出现这些问题

本轮抽查并重跑的两个 Loading 测试主要读取源码，用正则检查 TLoading、loading、zIndex、finally 等字符串是否存在。它们能够防止局部接入被误删，但没有真正挂载管理宿主、点击新建、断言 Drawer 内字段可交互。

因此这些测试通过与“新建按钮没有打开表单”可以同时成立。并不是全部测试都没有价值：另外两个本轮路由测试验证了实际路由/序列化行为，历史套件也有业务函数测试。问题是缺少覆盖当前失效链路的整页交互测试。

目前部分 R03 子批次使用 ACCEPTED_WITH_HOST_BLOCKERS，或 businessAccepted=true 但 Drawer 未挂载、管理宿主错误。若范围严格限定为 Loading 契约，这些证据可以保留；不能将其汇总为该页面业务可用。

任务数据还存在格式混用：R01/R03 的部分 verification.result 使用了现有 task.schema.json 枚举以外的值。这不是 UI 失效根因，但使程序化汇总/签收口径不一致。

应分开记录：源码转换完成、组件局部契约通过、整页业务场景通过、视觉通过、环境阻塞。任何必要上游交互失败，整页业务场景都应保持未通过。

## 5 建议调整实施优先级

暂停扩大以调用点数量为目标的 Loading/样式批量改造，保留已经有效的工作。先以能够操作的完整业务闭环为交付单位。

1. **先修管理宿主 R16 子批次。** 正确分离 Layout/Menu/主内容，验证集群、Grok、采集三个页面的内容宽度、菜单跳转和折叠。不要将整个 R16 未做的其他控件一起标通过。
2. **并行分析时间面板 P0。** 保留 R02 阻塞结论，建立 SDK 全依赖图的一致运行与面板所有权验证，恢复 16176 的完整时间操作。
3. **以集群新建修 Drawer/Form/Select 闭环。** 在 R11/R10/R08 中明确结构性试点的依赖和子范围：新建可打开、输入可更新、空表单校验拦截、合法测试请求、失败不关闭、成功回显、取消及未保存拦截。真正写入只用新建专用资源，不能编辑已有集群。
4. **修一个完整管理 Table。** 包含可见列、操作列、空/加载/错态、分页/排序/筛选及权限。完成后扩展同契约页面；动态列和高级选择另外列明。
5. **再回到共享控件扩展。** 将已经在完整业务中验证的协议推广到剩余调用；业务对象复杂性不同就拆批，而非机械标签替换。
6. **持续类型和最终宿主回归。** 不增加类型错误，逐批减少 1977 条债务；源码固定后再重建 APM/Trace，旧产物摘要不能继续当当前通过证据。

每批至少新增一个真实业务交互验收用例：点击入口→看到真实内容→输入或选择→业务状态/请求效果正确→关闭/取消/失败恢复正确。截图与当前源码摘要绑定；固定数据与真实接口分别记录。
