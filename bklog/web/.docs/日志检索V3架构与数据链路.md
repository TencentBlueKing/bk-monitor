# 日志检索 V3 架构与数据链路

> 本文基于 `bklog/web/src` 当前实现整理，重点描述日志检索从页面初始化、字段元数据、查询请求到流式结果落盘与渲染的完整链路。代码发生变化时，以当前源码为准。

## 1. 当前结论

- `/retrieve/:indexId?` 的默认实现是 `retrieve-v3`；只有 `localStorage.retrieve_version === 'v1'` 时才加载旧版 `retrieve/container`。
- 检索主查询不再是“Axios 请求返回完整结果后直接写入 Vuex”。当前链路是：主线程组装查询 → WebWorker 使用 `fetch` 请求 `/search/*?stream=true` → 解析 NDJSON/JSON → 结合字段元数据生成渲染信息 → 批量写入 IndexedDB → 通过 `row_keys` 和结果元数据回传主线程 → Vuex 驱动结果组件按需读取行。
- 行数据与结果元数据分离：Vuex 只保存查询状态、分页信息、结果元数据和行键；完整原始行存储在 IndexedDB，页面渲染时按行键读取。
- IndexedDB 存在能力检测和页面内存降级路径；Worker 服务负责检测、取消、超时和错误上报，避免页面直接持有大结果集。
- 查询存在三条后端分支：普通单索引、联合索引、场景化检索。字段元数据请求和主查询请求必须与分支保持一致。

## 2. 入口与模块边界

```text
router/retrieve.js
  -> views/retrieve-hub.tsx
      -> 默认 retrieve-v3/index.tsx
      -> 兼容 retrieve/container（仅 retrieve_version=v1）
```

V3 页面主要由以下部分组成：

- `views/retrieve-v3/index.tsx`：页面布局、搜索栏、场景筛选、结果容器、收藏夹和初始化状态。
- `views/retrieve-v3/use-app-init.tsx`：URL/空间/索引集解析、索引集列表、字段信息、场景配置、首屏查询、空间切换和卸载清理。
- `store/actions/retrieve-search-actions.js`：字段元数据请求和主查询 action，是检索状态与存储/Worker 之间的编排层。
- `services/retrieve.ts`：检索 REST API 定义及响应类型。
- `storage/services/retrieve-search-worker.service.ts`：主线程 Worker 管理、请求排队、取消、超时、进度和结果回传。
- `storage/workers/retrieve-search.worker.ts`：Worker 内 fetch、流式解析、结果落盘和异常分类。
- `storage/repositories/retrieve-row.repository.ts`：IndexedDB 行实体、批量写入、读取、渲染 overlay 和回收。
- `storage/services/retrieve-row-cache.service.ts`：查询键、行键、内存热点缓存、IndexedDB/内存降级。
- `storage/services/retrieve-field-cache.service.ts`：字段元数据规范化、内存缓存和 IndexedDB 持久化。
- `storage/core/db.ts`：Dexie 数据库及 `retrieveRows`、字段元数据、API 缓存、活跃查询等表结构。

## 3. 页面初始化链路

1. `RetrieveHub` 读取 `localStorage.retrieve_version`，默认进入 V3。
2. `use-app-init` 解析路由参数，写入 `indexItem`、空间和当前索引状态：
   - `index_id` → 单索引；
   - `unionList` → 联合索引；
   - `tags` → 按索引集标签匹配联合查询；
   - 无有效索引时优先恢复空间级最近索引，否则选择默认索引。
3. `retrieve/getIndexSetList` 获取分组索引集，前端扁平化并校验 URL/缓存中的索引是否仍有权限。
4. 场景检索开启时，`retrieve/requestSceneConfigs` 获取场景配置，并从 URL 回填场景筛选值。场景筛选为空时跳过字段和主查询。
5. 根据检索类型请求字段：
   - 普通单索引：`GET /search/index_set/:index_set_id/fields/`；
   - 联合索引：`unionSearch/unionMapping`；
   - 场景检索：`POST /search/scene/fields/`。
6. 字段响应经 `normalizeRetrieveFields` 规范化后写入 Vuex，同时按 `field_scope` 写入字段缓存；主查询必须等待字段元数据持久化完成。
7. 首屏默认 tab 为 `origin`，且字段存在时执行 `requestIndexSetQuery`；其他结果 tab 按页面交互触发对应能力。
8. 页面卸载时取消请求、释放当前查询的活跃标记和行缓存，并重置结果元数据、字段信息和检索运行态。

## 4. 主查询链路

### 4.1 查询参数与分支

`requestIndexSetQueryAction` 负责构造查询参数：时间范围、分页起点、关键字、结构化条件、业务 ID、联合索引配置等。

| 模式 | 请求路径 | 写入模式 |
|---|---|---|
| 普通首屏 | `POST /search/index_set/:index_set_id/search/?stream=true` | `replace` |
| 普通分页 | 同上 | `append` |
| 联合首屏/分页 | `POST /search/index_set/union_search/?stream=true` | `replace` / `append` |
| 场景检索 | `POST /search/scene/search/?stream=true` | `replace` / `append` |

查询开始前会生成 `row_query_key`。首屏查询释放上一查询的行数据；分页沿用当前查询键，并以当前行数作为 `startSeq`。请求通过 `RequestPool` 取消旧请求，Worker 侧使用 `AbortController` 终止 fetch。

### 4.2 主线程到 Worker

主线程向 `retrieveSearchWorkerService.searchStream` 传递：

- URL、请求体和请求头；
- `queryKey`、`startSeq`、`writeMode`；
- 字段元数据 `fieldMetadata`；
- 当前需要投影/展示的字段 `fieldNames`。

Worker 服务保证检索串行执行，维护 active request、超时计时器和 pending promise，并将 Worker 的 `meta`、首行 `row`、完成或失败消息映射回 Vuex action。

### 4.3 Worker 解析与落盘

`retrieve-search.worker.ts` 使用 `fetch` 发起请求，并补充 `Traceparent`。成功响应按 Content-Type 和响应内容选择：

- **NDJSON 流**：`parseNDJSONByteStream` 依次处理 `meta`、`row`、`done` 事件；
- **JSON envelope**：兼容后端未流式返回或 Content-Type 缺失的情况，读取 `data.list` 与 `data.origin_log_list`；
- 非 2xx 或协议字段不完整时返回结构化错误，不把异常结果写入页面。

每一行同时保留：

- `origin_data`：原始行，用于复制、上下文等原始数据能力；
- `data`：服务端渲染行，用于高亮和展示；
- `renderMeta` / `renderOverlay`：字段投影、截断、高亮叠加等渲染信息。

Worker 通过 `RetrieveRowStreamWriter` 按行数或字节数批量写入 IndexedDB，生成 `${queryKey}:${seq}` 行键。首行写入后发送一次进度，用于尽早计算默认列；完整行键在 `done` 后回传，避免流式过程中频繁重排表格。

## 5. 存储与渲染数据流

```text
后端响应
  ├─ meta / 结果元数据 ──> Worker progress ──> Vuex indexSetQueryResult
  └─ row / origin_data
       └─> RetrieveRowRepository
            └─ IndexedDB retrieveRows
                 └─ row_keys ──> Vuex
                      └─ SearchResultPanel / LogRows
                           └─ retrieveRowCacheService 按 key 读取并生成渲染行
```

### 5.1 IndexedDB 结构

数据库名为 `bklog-web-storage`。检索相关表包括：

- `retrieveRows`：查询键、序号、原始行、渲染 overlay、渲染元数据、过期时间；索引 `[queryKey+seq]` 支持分页读取。
- `retrieveFieldMetas`：按 `field_scope` 保存原始字段、规范化字段、字段树、别名索引。
- `retrieveFieldWidths`：服务端最大长度、计算宽度和用户宽度。
- `activeRetrieveQueries`：页面实例与活跃查询的心跳，用于 GC 时保护正在使用的查询。
- `apiCaches`：字段等 API 元数据缓存；结果行不依赖该表保存。

### 5.2 缓存和回收

- `RetrieveRowCacheService` 维护最多约 24MB 的行级内存热点缓存，并按 LRU 思路裁剪。
- IndexedDB 行默认 TTL 为 30 分钟；新查询、页面卸载和 GC 时释放旧查询。
- 活跃查询每分钟心跳，过期活跃记录会被清理；GC 会排除当前及其他活跃查询。
- IndexedDB 写入/读取失败时回退到页面内存，提示用户刷新后缓存不保留。

## 6. 并发、取消与竞态控制

- `RequestPool` 取消同类旧的字段请求和查询请求。
- Worker 服务通过 `searchQueue` 串行执行流式检索，避免多个流同时写同一查询缓存。
- 每次查询有独立 `queryKey`、请求 ID、页实例 ID；主线程在进度和最终结果应用前检查是否仍为当前请求。
- 过期响应只清理自身查询键，不覆盖当前 Vuex 结果。
- 首屏流未结束时，分页请求会被标记为 `initial-search-loading`，避免 append 抢占 replace。
- 分页取消属于控制流，保留已有行键和总数，不把正常竞态展示为错误。

## 7. 结果模块边界

V3 结果容器根据 URL `tab` 分流：

- `origin`：复用 `retrieve-v2/search-result-panel`，读取行键并展示原始日志结果；
- `grep`：Grep 查询和结果；
- `clustering`：日志聚类；
- `graph_analysis`：字段图表分析；
- 其他衍生能力包括趋势图、上下文日志、实时日志、导出和字段配置。

这些模块共享 Vuex 检索参数、字段元数据和查询结果元数据，但不应直接持有完整首屏行数组；大结果集应通过行键访问存储层。

## 8. API 清单（检索主链路）

- 索引集：`GET /search/index_set/`
- 普通字段：`GET /search/index_set/:index_set_id/fields/`
- 联合字段：`unionSearch/unionMapping`
- 场景配置：`GET /search/scene/scenes/`
- 场景字段：`POST /search/scene/fields/`
- 普通查询：`POST /search/index_set/:index_set_id/search/`
- 联合查询：`POST /search/index_set/union_search/`
- 场景查询：`POST /search/scene/search/`
- 趋势：普通 `/search/index_set/:index_set_id/aggs/date_histogram/`，场景 `/search/scene/aggs/date_histogram/`
- Terms：普通 `/search/index_set/:index_set_id/aggs/terms/`，场景 `/search/scene/aggs/terms/`
- 上下文：`POST /search/index_set/:index_set_id/context/`
- 实时日志：`POST /search/index_set/:index_set_id/tail_f/`
- 导出：普通、联合和场景分别由 `services/retrieve.ts` 中的 export API 定义。

## 9. 维护注意事项

1. 修改查询响应结构时，同时更新 JSON envelope 和 NDJSON 两种解析路径。
2. 修改字段结构时，先更新字段规范化与 `field_scope` 缓存，再确认 Worker 接收的 `fieldMetadata` 与展示字段投影一致。
3. 修改分页或取消逻辑时，必须保留 `queryKey`、`startSeq` 和 stale response 判断，否则可能出现结果串页或只显示部分行。
4. 修改行展示时，区分原始行、渲染行和 overlay，避免高亮/截断信息污染复制和导出数据。
5. 修改 IndexedDB 表结构时同步更新 Dexie 版本和 TTL/GC 逻辑，并验证 IndexedDB 不可用时的内存降级。
6. `retrieve-v2` 目前仍被 V3 的部分结果组件复用，不应将“V3 页面”误解为所有结果组件都已迁移到新目录。
