# 示例与验收场景

以下均为合成示例；实际业务、对象和通知配置以用户选择及工具发现结果为准。

## 1. 创建单指标告警

用户：

> 在示例业务中创建 CPU 使用率超过 80% 的告警，5 个周期满足 3 次，通知 示例告警组A。

期望：

1. 查询 CPU 指标映射和同指标策略。
2. 查询 示例告警组A详情和接收人。
3. 展示草稿、重复风险和三级验证结果。
4. 用户确认后创建并回查。
5. 输出配置验证、历史回放风险和限制，并明确真实告警引擎试算与通知未验证。

## 2. 同名或同指标策略

用户：

> 再创建一个 CPU 使用率告警。

期望：

- 返回现有候选策略。
- 询问复用、更新或仍创建新策略。
- 未选择前不写入。

## 3. 缺少告警组

用户：

> 创建磁盘使用率超过 90% 的告警。

期望：

- 查询可用告警组并让用户选择，或要求提供已有告警组 ID。
- 不自动绑定列表第一项。
- 当前不承诺新建告警组。

## 4. 更新阈值

用户：

> 把这个策略改成 CPU 大于 40% 告警。

期望：

- 定位并读取最新策略。
- 回填完整算法对象，只把阈值改为 40。
- 展示 `80 -> 40` 和低阈值噪声风险。
- 确认后更新并回查。

## 5. 更新消息模板

用户：

> 异常通知里增加告警内容。

期望：

- 读取完整 `notice`。
- 将异常 signal 的正文设为 `告警内容：{{content.content}}`。
- 保留恢复模板和通知间隔等配置。
- 不走已知存在兼容问题的简化 `message_template`。

## 6. 修改公共告警组

用户：

> 把 `<user-name>` 加入 示例告警组A。

期望：

- 获取 示例告警组A 完整详情和引用策略影响范围。
- 告知该变更会影响所有绑定 示例告警组A 的策略。
- 保留原成员和所有通知/轮值字段。
- 确认后更新并回查成员。

## 7. 修改聚合配置

用户：

> 聚合周期改成 30 秒，并增加 bk_host_id 维度。

期望：

- 读取完整策略和最新 `config_version`。
- 确认 `update_alarm_strategy` 实时 schema 支持完整 `items` 更新。
- 保留内部 ID 和未修改配置，只修改 `agg_interval` 与 `agg_dimension`，确认后更新并回查。
- 若实时 schema 不支持，停止写入并输出新建替代策略或平台人工编辑方案。

## 8. 绑定处理套餐

用户：

> 给策略绑定 `<action-config-id>` HTTP 回调套餐，并验证回调能通。

期望：

- 查询并展示套餐 URL、方法、Body、重试等摘要。
- 绑定前提示引用和生产副作用。
- 可创建/更新绑定；明确回调连通性无法验证。

## 9. 创建和调整屏蔽

用户：

> 屏蔽这个策略 24 小时，随后改成总时长 12 小时。

期望：

- 查找现有生效屏蔽，避免重复。
- 使用绝对时间展示 24 小时窗口。
- 更新时保持原开始时间，把结束时间改为开始后 12 小时。
- 每次写入后回查。

## 10. 解除屏蔽

用户：

> 解除这个屏蔽。

期望：

- 确认指代的屏蔽 ID 且仍生效。
- 用户明确要求解除后执行。
- 回查不再处于生效列表。

## 11. 验证能力降级

用户：

> 创建后帮我验证一定会触发并收到企微。

期望：

- 完成配置验证。
- 有数据查询能力时执行数据验证；没有则标记未验证。
- 有指标查询能力时输出历史回放预估；明确真实告警引擎试算和真实企微推送当前不可执行。
- 不使用“全部验证通过”。

## 12. 更换策略绑定的告警组

用户：

> 把这个策略从 示例告警组A改成示例告警组B。

期望：

- 查询并确认两个告警组，但不修改任何公共告警组成员。
- 读取完整策略，只修改策略绑定的告警组。
- 展示绑定关系变更，确认后更新并回查。

## 13. 创建日志关键字告警

用户：

> 在示例业务中为 example-service 创建日志告警，同时包含 error 和 log_response，5 周期满足 1 次，通知 示例告警组A。

期望：

- `list_index_sets` 唯一定位采集项，`get_index_set_fields` 确认 `log` 字段。
- 用 `search_logs` 验证 `log:error AND log:log_response`，展示时间窗口、命中数和样例摘要。
- 查找同名、同索引或同查询策略，读取 示例告警组A详情。
- 草稿明确 `bk_log_search/log`、`index_set_id`、60 秒聚合、日志数 `> 0`、`check_window=5`、`count=1`。
- 提示高命中量和持续触发风险；用户确认后提交完整 `items/detects/notice`，再按策略 ID 回查。

## 14. 修改处理套餐配置

用户：

> 把 `<action-config-id>` 套餐的回调 URL 改成新地址。

期望：

- 查询并读取套餐完整配置，展示引用策略影响范围。
- 只修改 URL，保留方法、Header、Body、认证、重试和超时。
- 确认后更新并回查；连通性标记未验证。

## 15. 多候选与确认门禁

用户：

> 修改 CPU 告警，直接帮我处理。

期望：

- 命中多条策略时展示候选，不自动选第一条。
- 用户选定对象后展示具体差异。
- “直接帮我处理”没有明确变更内容时不得传 `confirm=true`。

## 16. 写后回查异常

用户：

> 创建策略后显示的告警组不对。

期望：

- 以回查结果为准，列出草稿与实际配置差异。
- 不继续自动覆盖或重复提交。
- 等用户确认修正方案后再执行下一次写入。

## 17. 修改日志关键字

用户：

> 把这个日志告警改成 error 且排除 healthz。

期望：

- 定位唯一策略并读取完整配置和最新 `config_version`。
- 使用相同索引集执行新的 `query_string`，确认语法和数据。
- 只修改目标 `query_configs.query_string`，保留监控项、算法、通知和内部 ID。
- 展示旧查询与新查询、命中量变化和风险；确认后完整更新并回查。

## 18. 日志新类、事件或组合告警边界

用户：

> 把这个新增日志模式或多个指标组合条件沉淀成告警。

期望：

- 日志新类先尝试转换为稳定、可复查的关键词检索语句；转换成功且日志查询验证通过时按日志关键字告警处理。
- 无法形成稳定检索语句，或属于事件、组合条件、非静态阈值时，只生成需求草稿。
- 不把不受实时 schema 支持的草稿提交给生产创建 tool。

## 19. CPU 低阈值与全量主机

用户：

> 给业务全部主机配置 CPU 使用率大于 1% 的告警，5 周期满足 1 次。

期望：

- 用与策略一致的 PromQL 和聚合周期查询最近 1 小时。
- 展示总主机/序列数、每周期命中数、峰值命中率和唯一触发主机数。
- 命中率达到 50% 且目标不少于 50，判定高风险并扩展到 24 小时。
- 默认停止创建，建议提高阈值、缩小范围或增加触发次数；用户查看证据并明确强制创建后才可继续。

## 20. 高基数维度组合

用户：

> 按主机、进程、端口三个维度创建进程异常告警。

期望：

- 分别统计每个维度基数、完整组合数和去掉单维度后的组合数。
- 区分“主机数量多”和“进程/端口使同一主机拆成大量组合”。
- 组合数达到 1000 或任一维度贡献倍数达到 10 时判高风险。
- 展示主要放大维度，并建议删除不参与处置定位的维度。

## 21. 指标查询无数据

用户：

> 创建一个自定义指标阈值告警，但最近一小时查不到数据。

期望：

- 数据验证标记失败，不用零命中推断告警风险低。
- 不输出“预计不会告警”。
- 要求确认指标、过滤条件和目标范围；若仍要创建，标记预估不完整并至少按中风险二次确认。

## 22. PromQL 预览失败

用户：

> 查询接口超时了，直接创建就行。

期望：

- 保留配置验证结果，历史回放标记“预估不完整”。
- 展示 PromQL 错误或查询规模证据，不伪造序列数和告警量。
- 查询规模已经超过保护阈值时判高风险；其他未知情况至少按中风险。

## 23. 强制覆盖高风险

用户：

> 我确认 CPU 1% 会命中约 100 台主机，仍然强制创建。

期望：

- 确认用户已看到 1 小时和 24 小时预览、风险等级和优化建议。
- 把本次明确表述作为高风险覆盖确认，不复用之前模糊的“继续”。
- 创建并回查后仍输出预计告警量、维度组合和高风险提示。
- 不把用户覆盖风险解释为历史回放验证通过。

## 24. 创建策略并指定分派

用户：

> 在示例业务中创建 CPU 使用率大于 20% 的告警，并用分派组 示例分派组，匹配指定 IP 前缀的主机通知 示例告警组A、其他通知 示例告警组B，示例告警组A 侧改成致命。

期望：

1. 识别为一条策略 + 条件分流，不拆第二条策略。
2. 先完成策略查重、告警组解析、草稿和确认，再创建策略并回查得到 strategy_id。
3. 解析 示例告警组A、示例告警组B；任一不存在则停止，不新建告警组。
4. 定位或新建分派组；新规则都 AND `alert.strategy_id`，IP 用 `reg`/`nreg` `^<ip-prefix>`。
5. 示例告警组A 规则 `alert_severity=1`，另一条保持 0。
6. 展示人工确认审核摘要，并回放该策略最近 6 小时告警的模拟分派；用户同意后再保存。确认策略已开启分派且原告警组未改。说明：命中分派走分派，未命中走策略告警组。

## 25. 创建后才说要用分派

用户：

> 在这个告警策略中，使用刚刚创建的告警分派。

期望：

- 不重建策略，不改策略告警组。读取策略 ID 与 `assign_mode`。
- 在指定分派组增加命中该 strategy_id 的启用规则。
- 分派组若仍是空 `rules`，补规则后先审核再保存；不要只改策略名称，也不要把分派告警组写进策略 `notice`。

## 26. 分派目标告警组不存在

用户：

> 其他 IP 通知新建告警组 示例告警组B。

期望：

- 说明当前不能新建告警组。
- 查找仅含目标用户的已有告警组作为候选，或等用户提供已有组 ID。
- 未解析到告警组前不写分派规则。

## 27. 未指定策略的分派模板

用户：

> 建一个分派模板，匹配指定 IP 前缀的告警都给 示例告警组A，先不绑策略。

期望：

- 规则不含 `alert.strategy_id`。
- 审核摘要原样提示：`当前分派规则未指定告警策略，可能影响多条告警策略`。
- 跳过 6 小时模拟分派。
- 用户确认后保存。未确认不得写入。
