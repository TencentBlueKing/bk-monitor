# 告警创建与验证

## 环境与依赖

依赖同一目标监控网关的 `alarm-handling`、`alarm`、`metrics-query`、`metadata-query` 和 `log-query`。先确认目标环境和 `bk_biz_id`，再发现已授权工具并读取实时 schema；无法唯一定位或依赖不可用时停止对应步骤，不跨环境回退。下文只给出 Server 后缀，完整名称以目标环境发现结果为准。

把用户的“创建告警、调整策略、配置通知、指定分派、设置屏蔽”诉求，转换为可审阅的策略草稿、配置与数据验证和受控的生产写入流程。

## 触发场景

当用户表达以下意图时使用本技能：

- 创建、新建或沉淀单指标静态阈值告警。
- 根据日志采集项、索引集和检索语句创建或修改日志关键字告警。
- 接收日志新类、事件或组合条件的告警沉淀诉求；不能转换为确定日志检索语句时只生成草稿或转交后续扩展。
- 修改阈值、触发/恢复周期、监控目标、通知组、消息模板或处理套餐。
- 创建策略时指定告警分派：绑定已有分派组、按策略 ID / IP / 标签拆分通知、重置命中告警级别。
- 创建或修改告警时出现「a 条件告警给 A，b 条件告警给 B」：优先走告警分派，不拆多条策略。
- 查询或修改告警组成员、处理套餐配置。
- 创建、延长、缩短或解除告警屏蔽。
- 验证告警配置是否完整、创建后是否保存成功。

## 不适用场景

- “这个告警为什么触发、根因是什么”进入 告警诊断能力。
- 告警日报、周报、噪声治理进入 告警报表能力。
- 独立创建、编辑、删除告警分派组，或改与当前策略创建无关的分派规则，进入 `bkm-alert-assign`。创建/改告警时的条件分流仍由本技能先落一条策略，再按 `bkm-alert-assign` 写分派。
- 只查询指标趋势、不创建告警时进入 bkm-data-fetcher。
- 只查询日志或日志聚类时进入 bklog-query。

## 当前能力边界

- 稳定支持：单指标静态阈值、日志关键字计数阈值策略的查询、创建、完整更新和回查。
- 指标策略创建前使用 PromQL 历史回放预估目标范围、阈值命中、告警实例和维度组合数量；该结果是风险预测，不是真实触发验证。
- 日志关键字策略使用 `bk_log_search/log`，通过索引集和 `query_configs.query_string` 定义检索条件；创建前应使用日志查询 MCP 验证同一查询。
- 日志新类若可转换成稳定、已验证的关键词检索语句，可按日志关键字策略处理；否则与事件、组合条件和非静态阈值算法一样只生成草稿。
- 支持查询和更新已有告警组、已有处理套餐；不支持新建告警组或处理套餐。分派目标告警组必须已存在。
- 支持新建和更新告警分派组。策略上的告警组和分派是两套独立配置，互不改写对方。开启分派后：告警符合分派规则走分派，不符合走策略告警组。
- 分派不是策略上的 `assign_group_id`：策略 `assign_mode` 含 `by_rule` 后，由分派规则匹配。创建场景默认给规则补 `alert.strategy_id`。
- 规则写法、条件字段、级别重置和全局分派风险见 `bkm-alert-assign`。本技能只处理「这条策略」的分派绑定。
- 支持策略、告警实例、范围和维度屏蔽的查询、创建、编辑与解除。
- 完整更新可按实时 schema 修改日志 `query_string/index_set_id`、PromQL/时序查询和聚合配置；必须先读取完整策略并携带最新 `config_version`，保留内部 ID 和未修改字段。
- 指标元数据、可用维度、时序试查需依赖对应查询 MCP；真实告警引擎历史试算、真实通知推送验证和处理套餐回调调试当前不可用。
- “验证通过”只表示已完成相应级别的验证，不表示一定会触发或通知必达。
- 每次调用 MCP 前先读取目标 server/tool 的最新 schema。

## 验证等级

对外输出必须区分：

1. **配置验证**：必做。检查必填字段、规则结构、查重结果、告警组接收人和处理套餐配置。
2. **数据验证**：仅在有指标/日志查询 MCP 时执行；否则标记“未验证”，不要根据指标名推断有数据。
3. **历史回放预估**：指标查询 MCP 可用时执行，输出告警量与维度风险范围；不能表述为真实告警引擎试算。
4. **触发与通知验证**：真实告警触发和通知推送 API 未提供，标记“未验证”。可建议创建后观察实际告警，但不能声称已测试。

详细检查项见 [validation-checklist.md](./references/validation-checklist.md)。

## 通用安全规则

1. 所有操作限定在用户明确的 `bk_biz_id`；只有业务名时先解析并确认唯一业务。
2. 写入前必须查询并定位唯一对象。命中多条时返回候选，不自动选择第一条。
3. 更新前读取完整对象；嵌套的 `notice`、`actions`、`algorithms`、告警组和处理套餐使用读改写，保留未修改字段。
4. 展示草稿或变更摘要、影响范围和验证结果，再取得用户明确同意。
5. 只有用户明确要求执行写入时才传 `confirm=true`。
6. 修改公共告警组或处理套餐前，提示会影响全部引用对象；能查询时列出受影响策略。
7. 写入成功后必须回查；未回查或回查不一致时不得宣称完成。
8. 不把建议、草稿、接口返回警告或规划能力描述成已执行结果。
9. 中风险必须展示 24 小时扩展预览并二次确认；高风险默认停止创建，只有用户看到证据后明确要求强制创建才可继续。

## 默认创建流程

1. 解析业务、告警类型、数据源、指标/日志条件、目标范围和用户期望。若指令含「a 条件告警给 A，b 条件告警给 B」，检测规则仍是一条策略，分流走告警分派，不要拆成多条策略。
2. 判断是否为支持的策略类型：
   - 单指标静态阈值：确认指标数据源后继续。
   - 日志关键字计数阈值：先解析采集项/索引集和检索语句，使用日志查询 MCP 验证，再继续。
   - 事件、组合条件、非静态阈值或无法形成稳定检索语句的日志新类：生成需求草稿，说明能力缺口并停止生产写入。
3. 补齐阈值、比较符、聚合方式、聚合周期、触发次数、检测窗口、恢复窗口和级别。
4. 确认指标或数据源。主机指标可使用已维护的共享指标 reference；日志关键字通过 `list_index_sets`、`get_index_set_fields` 和 `search_logs` 确认索引与查询；其他来源缺少元数据时要求用户确认准确字段。
5. 用 `search_alarm_strategies` 按名称、指标、场景等查重。
6. 查询已有告警组和处理套餐；检查通知接收人是否存在。
7. 指标策略执行告警风暴与维度预览：先查最近 1 小时，中/高风险自动扩展到 24 小时；日志策略展示检索命中量风险。
8. 生成策略草稿和风险摘要，执行配置与数据验证。
9. 根据风险门禁处理：低风险正常确认，中风险二次确认，高风险默认停止并等待明确覆盖。
10. 向用户说明历史回放限制，以及真实触发和通知仍未验证。
11. 用户明确确认后调用 `create_alarm_strategy`。日志关键字必须走完整 `items + detects + notice` 路径，不能使用简化指标结构代替。
12. 用 `get_alarm_strategy` 回查并逐项对比草稿。
13. 用户指定了告警分派，或指令里有条件分流（a→A、b→B）时，策略 ID 落盘后再绑定分派，见「创建时绑定分派」，并执行 `bkm-alert-assign` 的人工确认审核。未指定且无分流则跳过，不要自动建空分派组。

## 更新流程

1. `search_alarm_strategies` 定位策略，`get_alarm_strategy` 读取最新完整配置。
2. 判断字段是否受实时 schema 支持：
   - 阈值：更新完整 `algorithms`。
   - 触发/恢复：更新 `trigger_config` / `recovery_config`。
   - 通知、消息模板：回填并更新完整 `notice`。
   - 告警组、处理套餐、目标、标签、启停：按 schema 支持字段更新。
   - 日志关键字查询：先用日志 MCP 验证新 `query_string/index_set_id`，再更新完整 `items`。
   - PromQL、时序查询、维度、聚合周期：仅在实时 schema 明确支持时更新完整 `items`，否则停止写入并说明能力缺口。
3. 展示变更前后差异和公共对象影响范围。
4. 携带最新 `config_version`，用户确认后更新，再回查确认。

消息模板不要默认走简化 `message_template` 字段；该路径已出现后端兼容错误。优先读取并提交完整 `notice.config.template`，只修改目标 signal 的模板。

用户要求该策略开启分派时，读取完整 `notice`，在 `options.assign_mode` 中保留 `only_notice` 并补上 `by_rule`，不要清空策略告警组。分派规则不在策略对象里，走「创建时绑定分派」。

## 创建时绑定分派

只处理当前这条策略。独立分派编排交给 `bkm-alert-assign`。创建和编辑分派必须人工确认审核后才能保存。

1. 解析用户指定的分派组名称/ID、优先级、匹配条件、目标告警组、是否重置级别。指令是条件分流时，每个分支写成一条分派规则。
2. `search_alarm_notice_groups` 解析每个目标告警组；不存在则停止，不能新建告警组，也不要自动绑列表第一项。
3. `search_alarm_assign_groups` 按名称或 ID 定位分派组：
   - 不存在且用户要新建：名称必填；优先级业务内唯一（越大越先匹配）。未给优先级时先列出已占用值，提出候选再确认。
   - 已存在：读取现有 `rules`，更新时传入完整规则列表（整组替换）；要保留的规则必须带回 `id`。
4. 已知当前策略时，默认给每条新规则补 `alert.strategy_id`。用户要做不绑策略的分派模板时不要自动补。
5. 规则必须 `is_enabled=true` 才会生效；`user_groups` 至少一项；`actions` 默认 `notice`。
6. 策略侧只确认已开启分派：`assign_mode` 同时含 `only_notice` 和 `by_rule`。缺 `by_rule` 时完整更新 `notice`，保留原告警组。不要改成只含 `by_rule`，也不要为了“走分派”去改或清空策略告警组。
7. 检查每条规则是否含 `alert.strategy_id`。未指定时审核摘要必须原样写出：`当前分派规则未指定告警策略，可能影响多条告警策略`，并跳过模拟分派。
8. 已指定策略时，按 `bkm-alert-assign` 的 simulate-assign：用 `alarm` 的 `list_alerts` 拉最近 6 小时并本地模拟，结果写进同一次审核摘要。
9. 展示人工确认审核摘要（含模拟结果或跳过原因），用户明确同意保存后才 `save_alarm_assign_group(confirm=true)`，再用 `search_alarm_assign_groups(group_ids)` 回查。

运行时：命中启用的分派规则 → 走该规则的告警组/级别；未命中 → 走策略告警组。配置层面互不改写。

常见用户说法：

| 用户说法 | 处理 |
| --- | --- |
| 使用分派组 X / 用刚创建的分派 | 开启 `by_rule`，在该组增加命中本策略 ID 的启用规则；策略告警组保持不动 |
| 匹配指定 IP 前缀的主机通知 A，其他通知 B | 两条规则：`ip` `reg` `^<ip-prefix>` 与 `nreg` `^<ip-prefix>`，都 AND 策略 ID。覆盖范围内走分派，未覆盖的仍走策略告警组 |
| 分给 示例告警组A 的改成致命 | 对应分派规则 `alert_severity=1`（0 保持，1 致命，2 预警，3 提醒）。不改策略告警组 |
| 只要分派、不要策略原通知 | 解释：未命中分派仍走策略告警组，不能靠关掉告警组实现。若希望某类告警不走策略告警组，把分派规则写到能命中它们 |

## 告警组与处理套餐

- 查询告警组成员时使用详情模式，成员可能位于 `users`、`duty_arranges[].users` 或 `duty_users`。
- 更新公共告警组必须保留通知时段、渠道、轮值、提醒和处理通知配置。
- 更新处理套餐前先读取完整 `execute_config`，保留 URL、方法、Header、认证、Body、重试和超时中未修改的字段。
- 当前不能新建告警组、处理套餐，也不能测试 HTTP 回调连通性。

## 屏蔽流程

1. 定位策略或告警实例，并查询当前生效屏蔽，避免重复创建。
2. 把“12 小时”“到明天下午”等自然语言转换为明确开始、结束时间和时区；冲突时先追问。
3. 展示屏蔽对象、级别、时间、周期、通知和说明。
4. 用户确认后创建、更新或解除屏蔽。
5. 用 `get_alarm_shield` 或 `search_alarm_shields` 回查。

## 输出要求

- 创建前：策略草稿、查重结果、通知配置、分派意向（组、条件、告警组、级别）、已指定策略时的 6 小时模拟分派、目标/序列范围、阈值命中、预计告警实例、维度组合、风险门禁和未验证项。
- 更新前：对象 ID、变更前后值、影响范围、能力限制。
- 写入后：资源 ID、实际保存配置、分派组/规则 ID、回查结论、未执行的验证项。
- 失败时：返回接口错误、已完成步骤和安全的下一步，不重复提交生产写入。
