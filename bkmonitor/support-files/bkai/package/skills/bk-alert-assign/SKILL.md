# 告警分派

## 环境与依赖

同一目标监控网关下的 `alarm-handling`（配置）和 `alarm`（告警事件预览）。

先确认目标环境和 `bk_biz_id`，再发现该环境已授权的 MCP 工具并读取实时 schema。下文的 Server 后缀不是可直接调用的完整名称；无法唯一定位或缺少依赖时停止相应步骤，不跨环境回退。宿主提供认证入口时使用该入口完成认证，不在 Skill 中保存凭据。

把“按条件把告警分给不同告警组 / 改级别”转成业务内唯一的分派组 + 启用规则。策略告警组和分派互相独立：开启分派后，符合规则走分派，不符合走策略告警组。

## 触发场景

- 创建、查询、修改、删除告警分派组。
- 创建或修改告警时，把 a 条件告警给 A、b 条件告警给 B（按 IP、标签、主机等拆接收对象）。
- 命中后把级别改成致命 / 预警 / 提醒。
- 给已有策略开启分派（符合规则走分派，不符合走策略告警组）。

## 不适用场景

- 创建或修改告警策略本体、阈值、屏蔽进入 告警策略配置能力。本 Skill 承接策略创建后的分派编排；目标环境未提供策略配置能力时应说明依赖缺失。
- 新建告警组：当前 MCP 不能创建告警组，只查询和更新已有组。
- 告警日报 / 根因分析进入对应巡检或 RCA 技能。

## 核心模型

分派组和策略是两套对象，**没有**策略上的 `assign_group_id`。

1. 策略告警组（`notice` 里的 `user_groups`）和分派规则是两套独立配置，改一边不要动另一边。
2. 开启分派：策略 `assign_mode` 含 `by_rule`，并保留 `only_notice`。运行时命中启用规则走分派（规则里的告警组/级别），未命中走策略告警组。
3. 分派规则用 `conditions` 匹配。绑定某条策略时默认加 `alert.strategy_id`；做不绑策略的模板时不加，保存前走未指定策略审核。
4. 分派规则里的 `user_groups` 必须是本业务已有告警组 ID，与策略告警组无替换关系。
5. 同业务内 **名称唯一、优先级唯一**；数值越大越先匹配。

`assign_mode`：

| 值 | 含义 |
| --- | --- |
| `["only_notice"]` | 未开启分派，告警一律走策略告警组 |
| `["only_notice","by_rule"]` | 已开启分派：符合规则走分派，不符合走策略告警组。这是正确开法 |
| `["by_rule"]` | 不要用这个去“关掉策略告警组”。告警组始终是未命中分派时的去向 |

## 当前能力边界

- 配置 MCP（handling）：`search_alarm_assign_groups`、`save_alarm_assign_group`、`delete_alarm_assign_group`、`search_alarm_notice_groups`、`get_alarm_strategy` / `update_alarm_strategy`。完整 Server 名称以目标环境的工具发现结果为准。
- 预览 MCP（告警事件）：已指定策略时用同一目标环境 **`alarm` 的 `list_alerts`**（缺维度再 `get_alert_info`）。不要用 handling 拉事件；查询结果为 0 时先核对环境、权限、时间及策略摘要。细节见 [simulate-assign.md](./references/simulate-assign.md)。
- Server 以工具发现为准。
- 可新建分派组；不可新建告警组、不可改数据链路内置分派组。
- `save_alarm_assign_group` 不传 `assign_group_id` 为创建；传入则为更新。更新时提交的 `rules` **整组替换**。
- 规则 `is_enabled` 默认可能为 false，要生效必须显式 `true`。
- 创建和编辑都必须先展示审核摘要，经人工确认审核后才能 `confirm=true` 保存。
- 已指定策略的创建/编辑：审核时拉取这些策略最近 6 小时告警，本地模拟分派；用户确认模拟结果后才能保存。未指定策略的规则不做调试。
- 每次调用前读最新 schema。

## 安全规则

1. 限定用户明确的 `bk_biz_id`。
2. 写入前查询定位；多命中展示候选，不自动选第一条。
3. 更新前读取当前组；保留未改的 name/priority/未提及规则 `id`。
4. **创建、编辑、删除分派组都必须经过人工确认审核后才能保存。** 「直接处理」「你看着办」「继续」不够。用户必须看到本次审核摘要，并明确同意保存这一次变更。
5. 已指定 `alert.strategy_id` 的规则，审核摘要必须带上最近 6 小时模拟分派结果；用户确认该结果后才能保存。模拟失败默认不得保存。
6. 规则 `conditions` 不含 `alert.strategy_id` 视为未指定告警策略。保存前必须原样提示：`当前分派规则未指定告警策略，可能影响多条告警策略`。这类规则**不做模拟分派**。用户确认提醒后才可保存，不要擅自补策略 ID。
7. 删除前确认不是内置组，`group_ids` 必须为数组。删除不做模拟分派。
8. 写入后回查；未回查不得声称完成。

## 条件分流优先走分派

创建或修改告警的指令里，只要出现「a 条件告警给 A，b 条件告警给 B」（不同 IP / 标签 / 主机 / 级别走不同告警组或人），**优先创建或编辑告警分派**，不要拆成多条策略，也不要把分流写进策略告警组。

处理顺序：

1. 检测指标、阈值仍是一条策略；条件分流是分派规则。
2. 策略尚未落盘则先按 告警策略配置能力 创建/更新这一条策略，再写分派。
3. 已知策略时给每条分派规则 AND `alert.strategy_id`。
4. 用户要做可复用、不绑策略的分派模板时，不要自动加策略 ID，走「未指定策略」审核。
5. 策略告警组保持独立，作为未命中分派时的去向。

## 人工确认审核

创建和编辑在调用 `save_alarm_assign_group` 之前，必须先输出审核摘要，停下来等用户确认。摘要至少包括规则草稿，以及（若适用）模拟分派结果，同一次返回。

```text
操作：创建 / 编辑
业务：<bk_biz_id>
分派组：<名称> / <ID 或新建> / 优先级 <n>

规则：
- 规则 <序号或 id>：条件 <...> → 告警组 <...>；级别 <保持/致命/预警/提醒>；启用 <是/否>；策略规则 <已指定 strategy_id=... / 未指定>

模拟分派：
- 已指定策略：最近 6 小时回放结果（见下）
- 未指定策略：跳过调试

审核项：
- [ ] 用户已审阅上述规则
- [ ] 已指定策略时用户已确认模拟分派结果
- [ ] 未指定策略时已展示提醒并获得确认
```

已指定策略时，按 [simulate-assign.md](./references/simulate-assign.md) 拉取告警、本地匹配，把汇总和明细写进本次审核。没有模拟结果（该做却没做，或查询失败未获用户接受）不得保存。

未指定策略时，审核摘要里必须单独出现这句，不得改写：

当前分派规则未指定告警策略，可能影响多条告警策略

同时写明「未指定策略，跳过模拟分派」。多条规则都未指定策略时，提醒只展示一次。

删除同样要审核：组名、ID、规则条数、是否内置，确认后再 `delete_alarm_assign_group`。删除不做 6 小时回放。

## 默认流程

1. 解析指令：条件分流（a→A、b→B）优先落到分派规则，而不是多条策略。
2. 解析业务、分派组名称/ID、优先级、规则（条件、告警组、动作、级别）。
3. `search_alarm_assign_groups` 查重名称和优先级。
4. `search_alarm_notice_groups` 解析每条规则的告警组；缺失则停止。
5. 绑定策略时 `get_alarm_strategy` 取 ID；开启分派则确认 `assign_mode` 为 `only_notice + by_rule`，不改策略告警组。
6. 检查每条规则是否含 `alert.strategy_id`。未指定则在审核摘要中写出固定提醒，并跳过模拟分派。
7. 已指定策略时，按 [simulate-assign.md](./references/simulate-assign.md) 用 `alarm` 的 `list_alerts` 拉最近 6 小时告警并本地模拟分派，结果写入审核摘要。
8. 展示人工确认审核摘要（含模拟结果或跳过原因），停等用户明确同意保存。
9. 审核通过后 `save_alarm_assign_group(confirm=true)`。仅当策略未开启分派时，才把 `assign_mode` 补成 `only_notice + by_rule`，不改策略告警组。
10. `search_alarm_assign_groups(group_ids)` 回查；改过策略则再 `get_alarm_strategy`。

删除：定位 → 确认非内置 → 人工确认审核 → `delete_alarm_assign_group` → 回查列表中已消失。

## 输出要求

- 写前：人工确认审核摘要；已指定策略的 6 小时模拟分派；未指定策略时的固定提醒；优先级占用；告警组接收人；策略 `assign_mode`。
- 写后：分派组 ID、规则 ID、实际条件与 `alert_severity`、回查结论。
- 失败：原始错误、未发生的写入、可执行下一步。
