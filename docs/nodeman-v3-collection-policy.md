# NodeMan V3：采集配置级部署策略

仅用于 `v3_fresh`；V2 与 Kubernetes 安装器不变。

## 本次适配

- 一份采集配置绑定一条 DeployPolicy，名称为 `bkm-collect-<采集配置ID>`。
- 创建、编辑、升级和整份配置主动执行复用同一个策略 ID。
- 主机/服务实例、拓扑、服务模板、集群模板和主机动态分组直接转成 Scope；只有 IP 选择需要查询 CMDB 补齐主机 ID。
- NodeMan 负责成员变化及 Scope 收缩后的收敛。按已确认的每小时自动触发机制接入，监控不再定时展开成员并重复下发。
- 监控仍持久化操作与 Trigger，保留任务轮询。Trigger 成功不等于采集实例已收敛，不能据此显示全部成功。

## 写入边界

先校验完整 payload，再锁定配置版本与策略绑定、保存操作记录；数据库事务提交后才调用 NodeMan。

同一绑定正在下发时拒绝并发提交；结果不确定时保留 `write_result_unknown` 并禁止自动重放。已明确接受的新期望状态可以更新原策略。

相同 payload 不重复执行；用户主动执行可以再次触发。操作返回的 `prepared` 只表示本地操作已建立，不表示 NodeMan 已接受或机器执行成功。

## 接入限制

- 使用已发布的包/模板和现有插件管理器参数生成能力。跨步骤 `step_data` 及动态插件文件模板仍明确阻断，不发送未解析的表达式。
- Exporter/JMX 独立实例使用 `specify_plugin_pkg`；其当前专门文档仍要求可产生模块身份的服务实例 Scope，主机粒度不在本次放开。
- 远程采集、停用/重新启用、卸载、回滚，以及指定部分实例/指定动作的执行仍未放开；不会用改 Scope 或 `enabled=false` 模拟停用。
- DeployPolicy 聚合 Workflow、反相与跨 spec 运行时参数的具体接口仍待补齐。任务详情、重试、终止和产品状态展示不作为本次已完成能力。
- NodeMan 侧同版本 context 更新的实际生效及 Scope 收缩、每小时触发周期，需要联调验收；本次只提交已有协议描述的期望状态。

## 数据升级

`0081_nodeman_collection_policy` 只为绑定新增策略 ID、最近提交的 payload 指纹，不删除旧目标记录。

检测到旧版逐主机 DeployPolicy 时明确阻断。需要先核对并处理旧策略，不能直接创建新策略造成双份采集，也不能只清空本地 ID 掩盖旧资源。

## 验证范围

回归覆盖 Scope 转换、策略创建/恢复/更新、编辑与升级、幂等提交、并发阻断、未知写入、事务回滚、旧策略保护，以及 V2 冻结契约。

本地使用隔离的 SQLite 测试库和模拟 NodeMan 响应；未代表真实 NodeMan、MySQL 并发锁或机器采集验收通过。
